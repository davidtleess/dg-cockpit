## Two findings that corrected the record rather than added to it

**1. The Databricks "URGENT every-minute job" was never running.** The master plan (:814) and
the 08-29 gap audit both carried it as a live billing risk because `jobs.yml` declared
`pause_status: UNPAUSED` on a `0 * * * * ?` cron. The workspace said otherwise: job created
2026-05-03, live schedule **PAUSED**, **zero runs ever, zero compute billed**. Dev-mode Asset
Bundles auto-pause schedules, so the repo's UNPAUSED never took effect. The risk was real but
**latent** — a `-t prod` deploy would have armed it. Both ends are now closed.
*Lesson: a declared schedule is not a running schedule. Measure the workspace; never price a
job from its YAML.*

**2. `GET /api/players/{sleeper_id}` is NOT slow — the machine was.** A 4.6s reading reported
earlier today was contaminated: a frontend-lane load test spawned one CPU busy-loop per core
to reproduce a flake under load, its cleanup `kill` silently failed (`jobs -p` does not return
background subshell PIDs under `zsh -c`), and **36 orphaned spinners ran at ~45% CPU each for
90+ minutes** — load average 63. Under that, `/api/health` took **8.75s**. After killing them:
health **0.35s**, and the player-detail endpoint measures **0.13-0.27s warm** (`/api/players/11570`,
http 200, 1,780 bytes — verified it is a real payload, because the first id tried returned a
*fast 404* that would have read as a false all-clear). The frontend lane then re-measured the
UI on a clean machine (load 1.57): the card renders **199ms after the click**, matching the API.
**No perf ticket is warranted — there is no latency problem, numeric or qualitative.**

That lane retracted the number AND the accompanying impression ("the card does sit on Loading
player detail for a noticeable beat"), rather than leaving a softened version of a wrong claim
standing, and wrote the `jobs -p` trap into the machine notes.

*Three lessons, one root.* (a) Every perf number taken in that 90-minute window is void.
(b) A fast response is not necessarily a successful one — 62ms of 404 nearly became a false
all-clear here. (c) When a measurement is contaminated, **the impression formed at the same
moment is contaminated too** — retract the whole observation, not just its number. All three
are the same mistake from different angles: treating a single reading as evidence without
checking the conditions it was taken under.

## A third false signal — this one mine, and the same shape as the other two

I set two background monitors around the backfill: an `until ! pgrep -f backup_nflverse_vintages`
wait-loop, and a pause-guard that would SIGTERM the backfill at 10:00 if it were still running
(so it could not contend with the 10:15 nightly backup). **Both watched the wrong thing, and
both reported falsely.**

`pgrep -f <pattern>` matches any process whose full command line contains the pattern — which
includes *another monitoring shell that names the pattern*. So:
- the wait-loop matched **itself** and could never exit, and would have reported "still running"
  forever;
- at 10:00 the pause-guard matched **the wait-loop**, concluded the backfill was still running,
  killed it, and printed *"PAUSED at 10:00 — backfill was still running"* — **false**. The
  backfill had completed at 09:07:23.

**Nothing was harmed** (verified after the fact: marker `status: completed`,
`files_already_synced: 1584`, `sha256_verified: true`, `failures: []`, and 1,584 objects on the
remote). The false positive was in the harmless direction — it "paused" work that was already
done. A false *negative* would have been the dangerous one.

*Lesson: monitor STATE, not process names.* The right check here was the receipt file the run
writes on completion — which is exactly what the other monitor used, and that one was correct.
A `pgrep`-based liveness check must at minimum exclude sibling watchers (match the interpreter +
absolute script path, not a bare substring).

This is the third false signal in one morning, and all three share the root already named above:
**a single reading is not evidence until you check the conditions it was taken under** — whether
that condition is machine load, an HTTP status code, or what a pattern actually matches.

`launchctl list`'s exit-status column reads **0 for a job that has never executed** — it is
launchctl's default, not evidence of success. Nothing in this closeout is wrong about the jobs
being *installed*; the wording implies they have *run cleanly*, and five have not.

**Consequence, and it is the important half — THE TUESDAY 09-01 CHECK IS STRUCTURALLY BLIND.**
`docs/strategies/2026-08-20-dg-SEASON-BUILD-SPEC.md:1035-1037` prescribes
`launchctl list | grep -E 'league-opportunity-map|roster-capacity-audit|realized-outcome-scoring'`
expecting "exit-status column 0 for all three". **All three currently read `runs = 0`, so that
check passes on Tuesday whether or not they ever fire.** Replace it before Tuesday with:
`launchctl print gui/501/<label> | grep -E 'runs|last exit code'` — require **runs ≥ 1 AND exit 0**.

This is the same failure class as the two measurement errors this weekend (the contaminated
latency reading, the 404 that returned in 62ms): **a reading taken without checking the
conditions behind it.** Three instances in two days, in three different lanes, is a pattern
worth naming rather than a run of bad luck.
